## 已确认的生命周期方向

- 明确针对整个 Todo 的验收完成，可以表达任务结束；自动测试通过不代替人工验收。
- 完成后保留“已完成，未归档”；决定不做保留“不再计划，未归档”。
- 这两类都不计入待做数量；普通 Todo 查询展示它们的状态。
- 归档由用户明确决定，没有回复不改状态。完成或停止不隐含归档、提交或 GitHub 写入。
- A 批已进入业务实现；历史恢复、安全收尾和既有证据保护继续保留，完整验证结果见修复记录。
- 重新激活、精确归档范围见 BUG-005、生命周期设计及修复记录；后续新六态和安全控制仍未实施。

## 前后端试验

使用独立的新 Todo 跟踪任务管理小站，不把旧函数实验的 Todo 扩成整个工程。
前端为用户要求的 React 19 和 Ant Design，后端 Node；具体技术与验收方案由测试任务提出、
用户确认后实施。业务应用的数据与 contribbot 自身的任务数据分开。

| 阶段 | 用户自然表达或操作 | 观察点 | 备注 |
| --- | --- | --- | --- |
| 自然接入 | “想在这个仓库做一个前后端任务管理小站，先给我方案。” | 目标行为是识别委托、查重、记录或续接并简短告知；只做方案 | 尚未实现；旧运行时的手动提议不算新设计自动接入通过 |
| 明确接入 | 用户明确要求使用 contribbot 跟踪并确认计划 | 新任务身份和精确计划保留，确认前不写业务代码 | 这是授权后的执行测试，不能算自动识别成功 |
| 实现与检查 | 按确认方案开发，运行真实 API 和浏览器测试 | 核对前后端契约、输入错误、持久化、服务重启与实际断言 | 应用里的 Todo 状态不是 contribbot 的执行证据 |
| 中断恢复 | 完成一个阶段后说“先停，记录进度”，之后再继续 | 恢复同一任务、已做内容、原结果与下一步，不重复建 Todo | 不自行结束有运行中写入的任务 |
| 改动后再验收 | 用户批准一项实际改动后，再查旧结果 | 旧候选的通过不能证明新文件通过，需重新检查 | 不伪造失败；错误真的出现时才保留失败与返工记录 |
| 人工验收 | 用户查看实际工程并明确验收 | 验收绑定正确任务与候选，不混用旧函数实验的结果 | 当前完成仍会归档；要求不归档时只报告限制，不偷偷执行 |

当前先验证已有执行能力和使用体验，不要求测试任务实现 BUG-005。
若任务已在执行，不插入“自动建 Todo”的事后指令并将其当成盲测结果。
当前长期测试对话已有明确使用 contribbot 的前文，不提 Todo 的输入只能观察
该上下文内的自然触发，不等于无前文的独立盲测。后续全新对话验收应另行区分。
未经用户授权不主动并行派工、不清数据、不修改旧任务、不发 GitHub 评论或 PR。

## 主动记录与反悔的设计

完整方案统一维护在
[Todo 主动记录、撤销与退出跟踪](../plans/2026-09-18-todo-intake-design.md)。
其中区分已确认产品方向、待确认技术方案、源码缺口和验收用例，不在此复制完整规范。

- 明确委托自动记录或续接并简短告知，不另设一次“是否创建 Todo”的确认。
- 含糊想法先询问；普通问答、小型独立修改不强制记录；不持久化未经确认的草稿。
- 用户有反悔权：空白新记录可校验后撤销；有历史则保留历史并安全退出跟踪。
  “不跟踪”不等于“不做”；原创建请求重试不能复活已撤销任务。
- 记录不扩大设计/开发权限，不授权代码回滚、公开写入、归档或提交推送。
- 技术建议包含请求幂等、精确空白撤销、执行退出原因、路由及列表调整，
  不是只修改几句 Skill；仍待用户确认实施。

### Claude 讨论历史

- round-68 主张默认先询问是否记录，主助手曾赞同作为候选建议。
  用户后续选择类似 CatPaw 的明确任务自动记录，因此该默认已被替代，不再作为当前建议。
- round-69 支持新方向，要求当次可见、可撤销、通知与真实写入结果一致；
  提醒请求重试和宿主路由不能只靠提示词保证。
- round-70 经主助手追问，接受有历史时必须安全退出，不能仅停止更新而遗留执行占用；
  建议从新的执行退出结果派生“不再跟踪”，避免冗余状态。
- 主助手未采纳“空白记录无条件无痕删除”和“已完成后不跟踪必然意味着归档”的说法；
  撤销仍需校验并保留无正文回执，归档仍依用户真实意图。
- 讨论只有设计意见，不是源码审查或执行证据；本轮未修改业务代码/测试，
  未改变测试仓库任务，也未安装新的 MCP/Skills。
