# contribbot 的 worktree 工作模式

日期：2026-09-16。状态：设计建议；本次没有创建 worktree、切分现有改动、commit 或 push。

## 推荐：一个主目录，三个用途，按需开工作空间

不要按照 Agent 数量创建长期分支。一个空间一次只负责一个任务，一名写入者。
建议保留 main 作集成入口，设计、开发、修复分开；短任务可以把设计并入开发空间。
目前一个人使用，不需要同时把所有空间开起来。

| 空间 | 职责 | 交付物 | 备注 |
|---|---|---|---|
| 主目录 / main | 总览、集成已验收成果、日常稳定使用 | 集成后的代码和工作记录 | 不与其他 Agent 同时在此开发；合并/提交/推送仍需明确授权 |
| design | 长期设计、Phase 3 拆解、方案比较和验收定义 | 文档、契约、范围与验收 | 不顺手实现业务代码；简单修复无需经过独立设计空间 |
| feature | 一项已确认功能的实现和测试 | 代码、回归、Evidence | 设计完成后在这里实现；不是无限堆积功能的永久 dev 分支 |
| fix | 复现问题、最小补丁、回归测试 | 失败复现、修复、验证 | 从包含缺陷的准确基线创建，不夹带功能重构 |
| review / spike（临时） | 独立检查、试验不确定技术路线 | 检查结论或实验答案 | 按需创建，用完检查后回收，不作为第四/第五条长期开发线 |

目录建议（这些路径是规划，不表示已创建）：

```text
D:/dev/darkingtail/contribbot/                       main
D:/dev/darkingtail/contribbot-worktrees/
  design-phase3/                                   codex/design-phase3
  feature-<topic>/                                 codex/feature-<topic>
  fix-init-upstream/                               codex/fix-init-upstream
  review-<topic>/                                  临时 detached HEAD
```

空间用途相对稳定，分支按任务创建、验收、整合后结束。不要让 design/feature/fix
三个永久分支各自积累数月再一次性合并。
Git worktree 提供独立工作目录、HEAD 和 index，但共享 Git 对象与部分仓库管理状态；
它不是容器，也不会自动隔离用户目录或进程。通常不能在两个 worktree 同时检出同一分支。

## 工作流

```text
需求 → design（复杂需求才拆出来）→ 方案确认
                                      ↓
main 已确认基线 → feature → 实现与测试 → 独立检查 → 用户授权整合到 main
       └──────→ fix → RED / GREEN / 回归 ────────────────┘
```

1. 先确认 Work、基线、可改文件、验收和写入者，再开任务空间。
2. 设计文档未整合时，开发不能假设 main 已包含它：明确引用已批准版本/文件哈希，
   或在授权后先整合设计提交。不要拿正在变化的聊天结论当成验收契约。
3. fix 如果修的是未合并 feature 的问题，默认在该 feature 上完成；
   确需分开时从其明确提交创建，而不是从不包含问题的旧 main 创建。
4. 检查者可只读检查 feature/fix；需要运行可写工具时用隔离临时空间。
5. 整合前确认改动、验证、未提交文件、分支独有提交和记录归属；
   main 只有一个整合者。先整合独立修复，再让依赖它的功能对齐。
6. 获准回收时使用 `git worktree remove`，先检查 ignored/untracked 文件；
   不用 `--force` 掩盖未保存内容，也不直接删目录。分支删除另行核对。

## 比 worktree 数量更重要的四个隔离点

### 1. 当前未提交改动不会自动出现在新空间

当前只有主目录 main，开发工具和项目归档均未提交，CatPaw 记录也未提交。
从 main 的 HEAD 新建 worktree，只得到那个提交，不会得到当前 dirty 文件。
因此先保持现状。正式启用前，用户选择授权提交现有成果，或明确做带校验的快照转移。
不能自动 stash、提交、清理主目录，也不能把“创建成功”当作接管了已有开发进度。

### 2. MCP、Skills 和依赖

- 每个需要运行代码的 worktree 自己安装依赖；`node_modules`、`.venv` 不通过 Git 传递。
- 当前 `dev:setup` 会更新用户级 MCP/Skills；不要在每个 worktree 轮流运行它，
  否则多个会话会争用全局开发入口，不能做到每个会话固定使用自己的源码。
- 暂时只保留一个明确的全局开发入口。实验空间用明确的源码路径启动 MCP，
  并在任务中明确读取该空间的 Skill 文件；不要假设目录变化就改变了 MCP 服务。
- 将来可设计 worktree-local 开发启动配置，但当前脚本没有“一键多空间隔离”的能力。
- Web 端口可以通过已有 `PORT` 分开；端口不同不等于数据目录不同。

### 3. 数据目前是共享的，不能并行自测写入

当前 MCP 与 Web 通过 Node `os.homedir()`、Agent 通过 Python `Path.home()` 使用
`~/.contribbot`，没有统一的 worktree 数据目录覆盖配置。
仅开 feature/fix 目录不隔离 Todo、配置、知识、巡检结果。

现阶段：最多一个空间对真实用户数据写入；其他空间使用已有测试的临时目录/临时 HOME，
不要为了切换数据而改变宿主应用的整个 HOME（这还会影响 Git/模型/宿主配置）。
`pnpm data:reset --yes` 清的是用户级 `.contribbot`，不是当前 worktree 私有数据；
执行前停止所有共享该目录的 MCP、Web、Agent/巡检进程。

下一步建议（未实现）：统一引入一个显式数据根覆盖，例如 `CONTRIBBOT_HOME`，
由 MCP、Agent、Web 和重置工具共同遵守，缺省仍使用 `~/.contribbot`。
先约定语义为“完整数据根目录”，再补端到端隔离测试；不能只改其中一端。
这是并行自测前的优先项，不必先增加更多 Agent 或工作空间。

### 4. CatPaw 工作记录

- 每个 Work 指定唯一负责空间/写入者；各空间的 `.catpaw` 不软链接到同一个可写目录。
- 开始任务时由主目录协调分配唯一 Work ID，再交给任务空间维护。
  其他空间保留旧副本时不并行更新该 Work；整合时保留其完整历史及 Evidence。
- 在实际受检空间执行 CatPaw 命令，candidate 必须对应那里的代码；
  不要在 main 的 board 上把 feature 的测试记录成“main 当前候选通过”。
- main 汇总时明确结果来自哪个分支/提交、哪些已整合、哪些尚未整合。
  整合若改变代码或契约，按影响面补验证，不改写旧候选的历史成功。
- 当前根 `AGENTS.md` 被 Git 忽略，新空间不会自动获得本机的项目 adapter；
  新空间接入时显式检查/添加入口，不能只复制看板便宣称宿主已接入。

## 最小落地顺序

1. 保留当前主目录和两个 Work，先补必要收尾，不搬运未提交代码。
2. 获得授权并形成清晰基线后，先开一个 feature 和一个 fix 空间；
   设计经常打断开发时再开 design。测试/review 暂时只读或临时空间即可。
3. 并行运行有状态自测之前，先统一数据根隔离，再做空间级 MCP/Skills 启动。
4. 使用一周后再决定是否需要 worktree 创建/初始化命令，不先搭复杂 Agent Team。

Git 行为依据：官方 `git-worktree` 手册（DESCRIPTION、COMMANDS、DETAILS）。
本项目入口与数据隔离限制依据当前源码，不表示未来版本已经支持设计中的配置项。
