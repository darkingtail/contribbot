## 本批行为

| 动作 | 当前行为 | 备注 |
| --- | --- | --- |
| 完成 | 关闭执行，保留 `done` 未归档 | managed 仍须通过原收尾门禁 |
| 决定不做 | legacy 使用 `not_planned`，managed 使用明确的 stopped completion | 保留结束原因，不自动归档 |
| 查看列表 | 分别展示已完成未归档、停止未归档 | 两者均不计入待做数量 |
| 归档 | 先预览，用户选择精确条目后移动历史 | 不顺手关闭尚未结束的执行 |
| 恢复展示 | `todo_restore` 保留终态及历史 | 不启动执行，也不表示重新开工 |
| 重新打开 | `todo_reopen` 回到 backlog | 保留稳定 ID，不创建新执行 |
| 重开并开工 | 明确授权后用稳定 ID 调用 `todo_activate` | 开新一轮，不复用旧轮检查作为新证据 |

完成、测试通过、归档、提交推送、GitHub 公开写入仍是不同决定。
普通任务、受管任务、本地 CLI 和 Issue 联动使用同一完成/归档边界。
完成后的任务可以留在列表里，同时其他任务可以获取原工作区开展工作；
未知进程、未处置操作和未完成的收尾预约仍然阻止冲突操作。

## 精确归档

1. `todo_archive(repo="owner/repo")` 只预览，不写任务数据。
2. 用户决定归档哪些条目后，仅传回所选的 `{todo_id, snapshot}`。
3. 每一项在锁内重算摘要，改变过的条目报失败，不扩大选择范围。
4. 中途失败逐项报告；原请求可恢复已写归档但尚未移除索引的条目。

没有稳定 ID 的旧终态记录必须显式调用 `prepare=true`，再检查返回的预览；
补 ID 不归档，也不能和 selections 在同次调用。未回答归档问题不产生动作。
预览中待恢复的两份记录不能当作一条新归档请求。

新增可选字段 `lifecycle_revision` 防止同日恢复或重开后复用旧选择：

- 缺失按 0 处理，但只读不会补写；它不是 Todo 主状态或执行 revision。
- 新恢复把版本递增和 `pending_transition=restore` 一起原子写入。
- 重试核对源归档版本加一与待恢复版本相等，只完成原移动，不重复递增。
- 无版本的历史 pending restore 在原移动上补版本，再删除归档副本。
- 重开递增版本；重复打开已处于 backlog 的同一条记录不再递增。
- 所有归档摘要和冲突比较保留版本；非法值、溢出或冲突拒绝继续。

这是增量写入兼容，不保证旧运行时与新运行时同时写同一份数据安全。
未批量迁移真实数据，未激活或安装运行时；试用时应先确认实际连接的 MCP 版本。

## 保留的保护

- managed 的候选、计划、检查回执、缺口声明、身份和结束意图校验不变。
- 重开后尚未创建新执行，不能把旧 managed 历史降级为 legacy 完成。
  Issue 入口在任何远端读写之前拒绝该路径。
- 已是停止态、没有打开执行时，重复停止只报告现状，不生成 closure 或修改历史。
  改动 branch/PR 或追加新笔记仍拒绝；相同内容只用于确认没有待写入的变化，
  不是请求身份、用户验收或验证通过的证明。
- 重复 Issue 收尾不重发评论或重复关闭。只有本地 done、没有远端回执时，
  明确报告“未刷新 Issue 状态”，不伪称 GitHub 已关闭。
- 旧版已经授权的 pending archive 继续按原请求恢复；不制造新的自动归档。
- 历史停止请求附带的 branch/PR 若与已保存值相同，可恢复；不同值不能覆盖。
- 恢复与重开要求精确 ID，别名或格式不一致在移动前拒绝，不先改后报错。
- 本地 `close` 结果为 `{schema_version: 1, todo, archived: boolean}`，
  普通新完成 `archived=false`；历史恢复按真实存储位置返回。
