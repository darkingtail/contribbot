用户发言时本轮检查及 attempt 尚不存在，不能事后补造当时已经看过新结果
的人工验收。也不能将助手编写、用户确认的方案说成“用户自己写的准则”。

| 核实入口 | 当前实现 | 备注 |
| --- | --- | --- |
| `packages/mcp/src/core/execution/contracts.ts` 的 `criterionSchema` | 区分 command、review、manual | 并非所有 Todo 都必须有人工作为必需项 |

| `skills/todo/SKILL.md` 的 done 流程 | 明确的整体验收与结束决定可以一次表达 | 已有规则，不应包装成全新能力 |

因此这是已观察的方案编写与交互编排问题，尚不能证明执行器的证据保护有错。
这次流程试验要求用户检查流程有其目的，不直接推广为普通任务的默认模板。

## 第一批已确认：减少不必要确认

普通方案按实际目标设置验收：命令能验证的事实用真实命令结果；
需要审阅的用审阅；确实需要用户判断的效果或体验才设人工项。
不机械添加一个叫 `a-user` 的必需项，也不禁止合理的人工报告审阅。
已经确认的方案不静默删项、降级或改写。

在既有授权内先完成可以执行的检查，再集中展示需要用户判断的内容。
不在检查尚未产生时先要求用户“确认全部结果”，然后再补一次验收。
真正的阶段决定、停止请求、缺失授权仍按各自边界处理，不能为减少轮数跳过。

当实际结果、约定交付与其余收尾条件已满足，用户对整个任务明确表达
“验收通过，可以完成”，同一条真实反馈可以支持适用的人工验收和完成决定。
逐项核对用户实际观察的对象；不能用对某一项的反馈代填其他未观察的人工项，
也不要求实际覆盖多项的同一句话拆成多次确认。
助手处理内部参数，不让用户照抄固定句式，不再追加一次“是否标记 done”。
单项认可、阶段验收、“可以继续”或测试全绿不能扩大为整项完成。

人工反馈是否仍有效，按它实际评价的对象和当前绑定判断，不仅看命令执行先后。
但本批不把发生在新 attempt 创建前的反馈迁移为该 attempt 的验收，
也不把提前说过的“完成”解释成未来任意结果都获得了批准。
如果用户在条件未满足时表达结束意图，应立即说明具体缺项，
不能让用户误以为已经完成，也不能声称他从未表达过完成意图。

完成依然不归档，不隐含提交、推送、关闭 Issue 等额外操作。
本批不新增主状态、意图状态机或自动完成调度器。

## 后续候选：明确的条件完成授权

例子：“当前效果我验收了，剩余测试通过后就完成，不归档。”
这可以是允许未来执行收尾的决定，不是对尚未发生的测试伪造人工验收。
与上一节“结果已齐全时一次结束”区分；跨结果等待、跨轮次恢复的可靠消费
需要单独设计与实现，不能只在 Skill 中加一句自动 done。

本轮讨论的候选边界是：只针对已经存在且明确的整项计划、执行与产物，
真实人工条件已满足，剩余条件可客观核验，用户明确授权通过后收尾。
系统保存授权的范围和原话，收尾时仍核对所有必需检查、交付和安全条件。
任务需看未来页面、未来测试报告或其他尚未完成的人工判断时，不适用。

方案、产物、执行周期或交付约定变化，失败、暂停取消、用户改口、
未处置操作或未知副作用均不能沿用该授权直接收尾。原话和历史保留；
不能把失败后重跑成功当成旧授权无条件复活，也不能默认用户接受缺口。
不能由完成授权伪造检查、豁免必需端点或授予 GitHub 写入权限。
具体存储与恢复契约尚未定案，本批不实现。

## 实施与验证建议

| 场景 | 预期 | 备注 |
| --- | --- | --- |
| 普通任务制定方案 | 不机械新增人工项；仍保留必要检查和文件内容审阅 | 需要宿主对话试验，不只测固定文字存在 |
| 结果齐全后整体验收并要求完成 | 正确记录真实反馈并收尾，只确认一次 | 端点、安全和整项覆盖门禁照常执行 |
| 只认可阶段或某一项 | 不完成整个 Todo | 不靠“完成”关键词做分类 |
| 多个人工项，只实际观察一项 | 其余项保持缺失，不从完成意图补造报告 | 一句话实际覆盖多项时可分别记录，不要求多轮用户确认 |
| 同一绑定的产物反馈早于独立命令结果 | 不仅因先后顺序宣称原反馈无效 | 本批不新增未来收尾授权；反馈必须符合原人工项的含义 |
| 必须人工看新结果，但新结果还未产生 | 如实说明缺项，不伪造人工通过 | 包含本次重开测试的情形 |
| 产物、计划或 attempt 已变 | 不复用旧轮反馈冒充当前验收 | 必须保留原证据 |
| 失败、未知操作、必需交付缺失 | 不绕过门禁完成 | 不因用户想结束就记录 verified |
| 正常完成 | done，未归档；不做额外公开写入 | 验证读回状态，不只断言调用返回成功 |

按确认范围审查 Skills、MCP 引导与已有单测的具体缺口，优先复用已有
证据和收尾能力，不因讨论新问题就重写执行器。新增行为需要定向回归，
自然语言误解与重复询问还需实际宿主验证，单元测试不能冒充完整体验验证。

前一咨询轮只更新设计和进度，没有执行新验证。用户随后确认第一批实施，
以下单独记录实现，不将后来的结果改写成设计时已通过。

## 第一批实现与验证

定位到 MCP 总规则仍有无条件“完成后主动询问是否标记 todo_done”，与相邻
一次完成规则冲突。已删除该无条件要求，将缺少决定与已有整项完成决定分开。
这是一处真实引导冲突，但不能断言它是所有宿主重复询问的唯一原因。

修改范围为 MCP 的 instructions、`todo_plan` / `todo_done` 描述、验收 Schema
说明、start-task / todo Skill 和执行参考。没有改状态机、收尾、候选捕获、
报告观察时间或验收证据校验，也没有新增条件完成字段。
复查后还修正组合链与两种周回顾提示中的归档表述。

执行参考明确：先做已授权且可执行的检查；同一条真实整体验收与结束消息
可由宿主在一轮内完成 report、读取新版本、inspect、close，不要求用户批准
每一次内部调用。确实缺少的判断仍说明原因并询问；已确认人工项不静默删除。
