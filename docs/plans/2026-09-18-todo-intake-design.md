# Todo 主动记录、撤销与退出跟踪

日期：2026-09-18。
状态：产品方向已讨论；本文的技术方案与新增交互待用户确认，尚未实现。
关联 Todo：`todo-proactive-intake`，`t-270ffa9e-b028-4245-b7bb-0e8d650fa405`。
本轮只整理设计、延续 Claude 讨论、更新已有任务记录，不改业务代码或运行时。

## 1. 一句话定义

用户正常描述要做的事情，contribbot 主动帮助记录和恢复；
用户不必管理工具，也始终可以拒绝、撤销记录或停止跟踪。

这里的“自动”是不增加一次“是否创建 Todo”的行政确认，不是不告知、不受控。
自动记录不能代替方案确认，不能把“先设计”解释成“开始写代码”。
不依赖 upstream、仓库知识库、Agent Team 或额外的 Work 系统。

## 2. 已确认的产品方向

- 明确的、多步骤或需要持续跟进的开发/设计委托，先查已有任务，再自动记录或续接，
  当次用一句自然语言告知；显式要求记录也进入同一套 Todo。
- 普通问答、小型独立修改不强制建 Todo；含糊的未来想法先询问，不先持久化再补问。
- 用户只说“先设计，不开发”，只能推进设计；任务存在不意味着实现方案已批准。
- 用户可以反悔；“不记录”“先暂停”“不做了”“删除”“归档”不能混为一谈。
- 完成与归档分离。“不做了”保留 `not_planned`，也不自动归档。
- 同一任务的历史应连续，不因换对话、换标题或再次打开就默认另建任务。

这些方向替代 round-68 中“所有新目标都先询问是否跟踪”的早期建议。
最新产品决定不等于已经改变当前安装的 MCP/Skills。

## 3. 什么时候记录

由宿主 AI 理解目标和上下文，工具负责确定性约束，不用关键词或文件数替代理解。

| 用户表达 | 目标行为 | 备注 |
| --- | --- | --- |
| “做一个前后端任务管理小站，先出方案” | 查重后记录，进入设计 | 通知明确“目前只做方案”，不写业务代码 |
| “把这个登录问题修好并补回归测试” | 属于独立可验收目标时记录或续接 | 是否需要持续跟踪由目标与风险决定，不按句式硬判 |
| “记一下，下周研究权限系统” | 建待办，不激活执行 | 明确记录请求不需要再问一遍 |
| “以后是不是可以做权限？” | 先讨论；有记录意图但不明确时问要不要记 | 没有答复就不写 Todo 或隐藏草稿 |
| “这个函数为什么这么写？” | 直接回答 | 不因出现技术词就创建任务 |
| “改一下这个错别字” | 轻量处理 | 除非用户要求，不强制持续跟踪 |
| “继续上次的权限任务” | 读取明确匹配的原 Todo | 多个候选就澄清；不凭相似标题合并 |
| “这次不要用 Todo，直接做” | 不自动记录，在原授权内做事 | 若已存在运行中的受管执行，先按第 6 节处理 |

适用前提是宿主已接入 contribbot，且当前项目身份明确、未被用户禁止跟踪。
工具每次仍显式传 `owner/repo`，不能把当前目录当默认 repo，更不能为记录任务
静默初始化另一个项目或恢复已归档项目。跨 worktree 使用同一个已解析的项目身份
及实际数据根；数据根不同必须说明，不宣称跨根自动查重。

## 4. 查重、告知与权限

### 4.1 先找目标，不按标题合并

优先级是显式 Todo ID/ref、当前会话已绑定任务、目标与边界明确一致的候选。
相似目标可能是不同任务，也可能是旧目标新增范围；有实质歧义就问。
同一整体目标的前后端步骤留在一个 Todo 内，不把每轮对话都变成一项。
查看已完成或已归档的旧任务，不等于重新激活。

### 4.2 只有写入成功才说“已记录”

成功后的通知示例：

> 已把“任务管理小站”记为 Todo，这轮只出方案。你可以随时说不要跟踪。

不承诺“随时无痕删除”，因为随后可能产生真实执行历史。
工具明确失败时说明未记录；响应超时、结果未知时先查回执，
不能换一个标题重新创建，也不能向用户宣称成功。
记录失败不必阻塞已获授权的普通问答或轻量工作，
但不能把没有记录的执行说成受管、可恢复、已验证。

### 4.3 记录与执行分离

```text
明确委托 -> 查找已有 Todo -> 记录或续接 -> 简短告知
                                            |
                                     按原委托范围推进
                                     /              \
                                  只记待办         设计/开发
                                  不激活          建立执行上下文
```

新建记录本身是 backlog；开始实质设计也属于工作，应建立执行上下文。
不能为了让记录保持“可空白撤销”，故意不记录已经开始的设计和操作。
计划确认、公开 claim、Issue/PR 写入、提交推送、归档仍分别遵循原有权限要求。
“已记录”是通知，不是通过用户未反对来获得新授权。

## 5. 反悔的交互

以下区分用户已认可的“可以反悔”与本文提出的具体实现方式。

| 用户意图 | 处理 | 备注 |
| --- | --- | --- |
| “刚才那条不用记” | 符合空白撤销条件时撤销本次新建 | 不是 `not_planned`，不删除一个被复用的旧任务 |
| “先停一下” | 不派发新工作，处理运行中操作，保留恢复点 | 暂停不是结束或验收，不伪造进程已停止 |
| “这件事不做了” | 安全结束当前执行，保留 `not_planned`、未归档 | 不回滚代码，不等于检查通过 |
| “继续做，但不要跟踪了” | 安全退出跟踪，保留代码与已有历史 | 新增设计，见第 6 节，不谎称任务已经放弃 |
| “把记录也删掉”且已有历史 | 展示精确对象、历史和关联影响，再确认删除 | 普通撤销不调用 `force`；运行中或未完成收尾时不删 |
| “还是继续这个任务吧” | 保留原记录时恢复同一 Todo | 若之前拒绝的是跟踪而非工作，不能把“继续开发”当恢复跟踪 |
| 已撤销空白记录后明确要求重新记录 | 新请求、新记录 | 已真正删除的记录不能声称保留原历史；原创建请求不能复活 |
| “完成了，先别归档” | 整体验收满足后保留 done、未归档 | 完成不隐含归档；当前实现仍待 BUG-005 修复 |

对象与含义清楚时不再增加机械确认；有历史、删除范围或“停止工作/停止记录”
含义不清时，只问一个能解除歧义的问题。

### 空白撤销条件

必须同时满足：本次确实新建、精确 Todo ID 与创建回执匹配、版本未变化、
没有任何执行历史、没有操作/claim/依赖等关联、实现文档仍是本次生成的未修改记录。
模板自动生成的内容不算用户新增内容，但需要校验归属与内容指纹。
“没写业务代码”“没有测试结果”“刚刚创建”都不是足够条件。

撤销只删除这条自动创建的本地 Todo 及其归属明确的原始文档。
不碰项目源码、用户文档、Git 历史、其他任务或远端评论。
校验失败就解释为什么现在不能当作空白记录撤销，并进入保留历史的路径。

## 6. 有历史时退出跟踪（待确认的新增设计）

单纯“不再更新”会留下仍被认为 active 的受管执行；
直接标记 `not_planned` 又会把“不跟踪”误写成“不做”。
建议将“是否还在跟踪”作为独立的展示语义，不再增加一套业务 Todo 状态。
采纳 round-70 的简化：从最新执行结果派生，不再重复持久化一个 tracking 开关。

- Todo 保留退出时最后观察到的业务状态；最新执行以非成功的 `tracking_stopped`
  outcome 结束，而非 `done` 或 `abandoned`，关闭时间就是退出时间。
- 仅当最新执行已如此关闭、且没有后续执行时，展示为“不再跟踪”。
  这不是新增业务状态，也不是另建一套长期偏好。
- 保留计划、代码、证据、历史；不自动归档，不关闭 GitHub Issue/PR。
- 普通列表单列“已停止跟踪，最后已知状态为……”，不计入实时待做数量。
  明确这是历史快照，不能继续展示为实时进行中或当前验收通过。
- 用户明确恢复跟踪时，读取真实文件和任务现状，保留原 Todo ID，
  在先前执行已关闭的前提下建立新执行，旧结果不能自动成为本轮通过证据。

安全退出顺序：

1. 停止新派工；识别当前执行、运行中操作及正在收尾的意图。
2. 在既有授权内停止或等待当前操作结束，并核实执行者/进程/回执；
   需要额外破坏性动作时另问，不直接杀掉不明进程。
3. 有 running/unknown 操作、returned 未处置结果或未解决的 `closing_id` 时，
   拒绝最终退出，不后台排队，不提前释放占用；先完成真实核查和结果处置。
   已开始收尾必须先恢复/对账原意图，不能用退出覆盖可能已发生的远端副作用。
4. 在同一受保护收尾内以新 outcome 结束执行并保留历史，之后才能释放占用；
   跟踪展示从该执行结果派生。
5. 按用户原委托决定是否继续普通开发；没有完成退出前，
   不启动会与原执行竞争同一工作区的新写入。

已完成且没有打开执行的 Todo 不应为退出跟踪凭空新增一个执行。
“以后不用主动跟踪”是未来偏好，不自动改动所有历史完成项。
同理，没有打开执行的历史终态无需再次关闭。
“不要跟踪”不必然表示“不要显示”：先说明当前已经没有运行中的工作；
只有用户确实想收起或删除历史时才分别讨论归档或删除，不替用户猜。

这一部分需要新的收尾分支与兼容读写，不是现有 `todo_update` 就能做到。
若暂不实现这条路径，只能诚实支持“暂停并说明限制”，不能宣称完整支持退出跟踪。

## 7. 技术设计建议

### 7.1 各层责任

| 层 | 责任 | 备注 |
| --- | --- | --- |
| 宿主路由、MCP instructions、init 输出 | 让自然开发委托能进入 Todo 工作流 | 不是后台监听所有聊天；不为每项任务重新 init |
| Todo / start-task Skills | 识别意图、查已有目标、通知、澄清、原授权内推进 | 工具结果不是用户授权，外部资料不是用户指令 |
| MCP 工具 | 校验精确对象、请求幂等、撤销资格、结构化返回 | 不做标题语义判定，不启动 LLM/Agent |
| TodoStore / RecordFiles | 锁内校验、版本和文件归属、可恢复的索引/文档写入 | 进程中断不能留下被宣称成功的半次创建或撤销 |
| 执行收尾 / 列表 | 安全退出、占用释放、历史状态呈现、待做统计 | 复用现有收尾约束，不开放强制绕过 |

具体工具名与字段是方案，不是当前已提供的 MCP 能力：

- 扩展 `todo_add`：自动接入携带不透明 `request_id` 和来源，
  返回 `created / existing / undone / conflict / recovery_required` 等明确结果及稳定 ID。
  老调用保持兼容；自动接入路径必须有可重试身份。
- 新增窄用途的 `todo_undo_create`：精确 ID、原创建回执、预期版本；
  不接收 `force`。复用存储保护，不把普通删除改成自动撤销。
- 增加执行的 `tracking_stopped` outcome 及受管安全收尾分支；
  更新归一化、关闭门禁、普通/受管路径、恢复指导和派生列表投影。
  项目列表、dashboard、Web 的统计都要排除已退出执行的实时待做数，
  详情仍能查历史，不能只改 Todo Skill 提示词。
- 记录创建来源和必要回执，不保存完整聊天、推测的需求或未经确认的实现方案。

### 7.2 重试和并发

`request_id` 由宿主为这一次建任务动作生成并保留，不能由标题或需求内容推导。
同一次动作重试使用原 ID；同一项目数据根下两个进程使用相同 ID 只得到一个结果。
同一 ID 携带不一致参数应报冲突，不能悄悄改写目标。

创建成功但通知丢失时按回执读取既有结果；中断在索引和文档写入之间时，
恢复同一动作并检查归属，不留下第二条任务或覆盖用户编辑。
撤销要有同等的崩溃恢复能力；即使重复请求也只撤销本次创建。
锁保护工具间并发，文档还需要内容指纹/归属校验，不能假设没有外部编辑。

撤销后保留极小的无正文回执，记录不透明请求键和“已撤销”结果，
防止迟到的原创建请求重建任务。这不是隐藏 Todo 或语义拒绝库，
不保留任务正文；也不承诺删除宿主原有聊天记录。
回执清理必须同步界定过期请求的拒绝规则，不能清掉后把旧请求当新建。

不同宿主用不同请求 ID 提交相近目标，仍需要语义查重或澄清；
本设计不宣称跨独立宿主的任意任务 exactly-once。

### 7.3 拒绝后不反复创建

当前已知会话内拒绝的是同一个意图，不因换标题、改写句子就重新建。
不把拒绝的完整内容偷偷存进另一个数据库。
跨会话没有可用上下文时不承诺记得此前拒绝；
机械重试的无正文回执不能识别另一会话的语义相同请求。
持久项目偏好可以后续独立设计，只有用户明确要求才保存，
本轮不新增全局自动记录开关或默认修改所有项目。

## 8. 当前能力与缺口

以下依据本轮读取的本地源码，不表示已实施本文方案：

- `todoAdd` 已创建索引与实现文档，但没有请求级幂等参数；
  自定义 ref 去重与自动 slug 加后缀不等于语义/请求去重。
- `todoActivate` 会立即创建执行，所以已进入设计的任务不再是无历史空记录。
- `TodoStore.deleteUnlocked` 拒绝删除打开的 managed 执行，
  有历史时要求显式 force；不能复用为安全空白撤销的全部契约。
- `todoDelete` 在保存索引后删除文档；创建也涉及多个文件，
  一个进程内锁不等于多文件崩溃恢复事务。
- 当前执行 outcome 只有 done/abandoned；stopped 收尾会映射到 not_planned。
  尚无第 6 节的退出跟踪语义。
- 当前完成/决定不做仍涉及自动归档，BUG-005 尚未实现。
- 当前 Skills 的显式任务触发不证明自然输入会自动加载；
  必须验证路由上下文，不宣称所有宿主都能可靠识别。

`packages/mcp/src/core/storage/todo-store.ts`、`record-files.ts`、

## 9. 实施顺序与验收

用户确认本文后再实施，交付范围不是只改几句 Skill 提示：

1. 先落实 BUG-005 的完成/停止与归档分离，保留旧数据恢复和收尾保护。
2. 实现请求幂等、可恢复创建、空白撤销与保留历史的安全退出，补工具和存储单测。
3. 接通路由、Skills、通知、列表及恢复说明，同步不再适用的旧规范。
4. 使用隔离数据做 MCP/CLI 集成测试，再经用户同意做真实宿主试用；
   不以直接调用工具成功代替自然输入识别验证。

| 验收场景 | 必须观察到的结果 | 备注 |
| --- | --- | --- |
| 自然委托且未说 Todo | 查重后只建一条并简短通知 | 分开测已有 contribbot 上下文和全新对话 |
| “先设计，不开发” | 可以记录和设计，不写业务代码 | 建记录不是计划确认 |
| 含糊想法没有答复 | 没有 Todo、草稿或拒绝正文落盘 | 直接查看隔离存储 |
| 普通问答/小改/明确拒绝 | 不强制建任务 | 不阻止原已授权的普通工作 |
| 明确续接与相似不同目标 | 前者复用 ID，后者澄清 | 不靠标题哈希合并 |
| 创建落盘后响应丢失 | 原请求重试返回同一 ID | 不能补建第二条 |
| 同键并发、参数冲突 | 单一结果或明确冲突 | 不承诺不同键的语义去重 |
| 创建/撤销中途退出进程 | 可恢复一致状态，无错误成功通知 | 覆盖索引与文档各写入边界 |
| 空白撤销及其重放 | 精确删除原始记录，重放不复活 | 无 force、无源码删除 |
| 激活、文档修改或关联后撤销 | 拒绝空白删除，指出保留历史路径 | 版本与内容指纹都要覆盖 |
| 退出跟踪时仍在运行/收尾 | 不提前释放占用，不启动竞争写入 | 进程停止需真实核查 |
| 安全退出跟踪 | 历史保留，执行非成功结束，列表不计实时待做 | 不伪造 done/not_planned/归档 |
| 不做了、完成了、再次打开 | 终态未归档；恢复同 ID 和新执行 | 旧验收不复用为新候选通过 |
| 拒绝后换标题再表达 | 同会话同意图不重复创建 | 新会话记忆限制如实报告 |
| 不支持自然路由的宿主 | 报告覆盖缺口 | 不把有前文提示的实验当盲测 |

### 取消状态简化的风险分析（仍待决策）

用户尚不确定是否采用简化，要求先分析隐患。Claude 同一会话 round-73 已返回意见；
本节仅记录分析，不视为用户同意，不实施状态或数据迁移。

- 合并终态的实际取舍：仅按状态无法区分“未开展就放弃”和“已有部分工作后取消”。
  两者都不算完成、都不再进入待做、都保留历史并可重新打开时，可以共用结束逻辑，
  但这不足以证明必须共用状态。列表理解、常用筛选和统计也能支持拆分；
  不同重开规则或自动处理行为不是唯一条件。详情仍须保留已知事实和结束意图，
  不能按难以可靠判断的“开工程度”自动分类。
- 取消不同于暂停。“先不做”“暂不做”含糊时澄清，不能直接结束任务；
  测试失败也不是用户取消。此前示例把“暂不做”写成取消原因，不应作为路由规则。
- 受理取消与安全结束必须分开：先阻止新业务派工，仍核查、回收和处置已运行操作。
  请求必须能在中断后恢复，不能只靠会话中的一句话或 Next 备注。
  仍有未知操作或未对账的远端收尾时，不宣称已安全取消、不提前释放占用。
- 取消不应要求任务先通过验收或补齐完美的工作总结。记录当时已知的内容，
  缺失就说明未记录；已取得的真实结果照实保留，不能一概改成未知或失败。
- 重新打开保留 Todo ID，但使用新执行身份。旧执行的迟到结果不能改变新一轮；
  取消尚未完成时仍要接收和处置原操作的有效回执，不能一律丢弃。
- 旧 not_planned 缺少原因或来源时不补造“用户取消”“未开始”等事实，
  不批量改写历史。已完成轮次也不能被之后的取消覆盖。
- 取消不触发归档、代码回滚、删除、关闭 GitHub Issue 或新的跟踪退出机制。
  完成与归档耦合是现有问题，增加 cancelled 枚举本身不能解决它。

- 采纳一个非完成终态与“受理/结束”分离的建议，作为待确认方案。
- 不采纳一并禁止 yield/核查的说法：现有安全收尾可能需要候选核验和 yield，
  应禁止新业务工作，而不是禁止完成安全退出所需的操作。
- 不采纳将原操作终局结果一律标未知；只对确实无法核实的部分保持未知。
- Claude 将当前 stopped 描述为没有原因并不准确：closure 中已有 decision/note，

取消收尾可中断恢复、重开后旧回执不能污染新执行、旧数据不补造事实、

### Todo、Issue 与领取动作的边界

用户明确要求区分 Todo 与 Issue：Todo 的来源不止 Issue，不能用 Issue 状态代替
任务生命周期。本节继续设计，不修改代码；前面的状态清单是实现现状加已确认增项，
不是对全部现有状态作为未来领域模型的批准。

- Todo 是独立任务，围绕目标、执行与验收组织。用户委托、想法、Issue、
  上游变更或巡检发现都可以成为任务来源；没有 Issue 也须支持完整生命周期。
- Issue 是外部协作对象，有自己的状态；PR 是可关联的交付与评审对象。
  来源解释任务为什么产生，关联描述任务与哪些外部对象有关，二者不混同。
- 当前公开 claim 是在 Issue 评论中声明领取工作项的协作动作，
  不是 Todo 或 Issue 的主生命周期状态。
- Todo 的执行者分配、Agent 委派与公开 claim 分开设计；
  本地任务不应被强制要求公开认领，也不意味着所有 Todo 都必须增加分配步骤。
- 不假定一个 Issue 与一个 Todo 必然一一对应；具体关联结构另行设计，
  本轮不引入新的通用集成框架。

本轮代码核对发现的现有耦合：

- `todoClaim` 要求 `#issue` 引用，发布评论后更新 `claimed_items`，并可能把 Todo
  设为 active。这是现有 Issue 联动行为，不应作为所有 Todo 的激活前置条件。
- `prCreate` 关联 Todo 时把状态改为 pr_submitted。
- `issueClose` 存在本地完成联动，旧路径仍涉及自动完成与归档；
  managed 路径另有显式 completion 和验收/安全收尾门禁。

建议明确的联动边界：

1. 完成或取消 Todo 本身不授权关闭 Issue、发布评论或撤回公开认领。
2. Issue 关闭或 PR 提交本身不证明 Todo 目标已完成。

3. 保留显式且已授权的联合操作；分别记录本地与远端结果，并支持部分失败恢复。
   要求远端回执的联合收尾本身不违反状态独立，不能因此删除现有安全门禁。
4. 有公开 claim 的 Todo 被取消时，可提示用户是否撤回声明，
