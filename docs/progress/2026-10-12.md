### 跨仓库流程的静态缺口

`todoAdd` 在 `packages/mcp/src/core/tools/core/todos.ts` 使用管理主体的 owner/name
查询数字 Issue ref；`todoActivate` 也使用同一主体读取 Issue 与评论。
因此将 makeplane/plane 的编号直接作为 darkingtail/plane 项目的 `#编号`，
会去 fork 查询，无法仅凭编号保留源仓库身份。todoAdd 查询失败还会使用默认值
继续创建，创建成功本身不能证明关联正确。

`packages/mcp/src/core/tools/linkage/pr-create.ts` 的同一个 repo 同时决定远端
PR 目标和本地 Todo 存储；`todoUpdate(pr=编号)` 同样将 PR 解释为管理主体仓库。
底层 PR 数据结构能保存完整仓库身份，但不能据此声称上述公开入口已经提供
管理主体与交付仓库的独立参数。本轮只确认代码行为，没有执行错误仓库调用
或远端写入来复现，也不笼统认定所有跨库路径均不可能使用。

这项发现让 Plane 的第一项试用应优先检查 fork、parent、Issue 和 Todo 归属。
普通入口无法表达时，应保留完整来源链接并如实报告缺口，不把 Todo 自动搬到
parent，也不把外部编号冒充 fork 本地编号。没有在本轮自行设计或实施修复。
